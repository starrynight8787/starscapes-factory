The print page transferred 15,595 KiB.

WHAT THIS DOES (items 2 and 3 of the list, plus the part of item 1 that can be done safely, plus the cause of most of those 15 MB)
 A. THE PRINT PAGE NO LONGER DOWNLOADS EVERY SIZE'S PICTURE. It used to fetch the pictures for all 8 sizes and frames 0.8 seconds after opening ("so that changing size feels instant"). On a phone that competed with the main photo
    for the connection, and was most of the 15 MB. Now a picture is fetched only (1) when the shopper reaches for that size or frame (hover, focus or touch), and (2) the one they are most likely to want next (the same size in the
    other finish) once the main photo has FINISHED loading and the browser is idle. Each picture is fetched at most once, and nothing is fetched if they leave first.
 B. THE MAIN PHOTO STARTS DOWNLOADING EARLIER (item 3). Each print page's head now has a preload for the picture the page shows first: the first size's own picture (not the artwork; the artwork stays the link-preview and pin picture),
    marked high priority, no crossorigin (so it is the same download the page then uses). It is worked out when the site is built, from each print's own sizes. A print whose first size has no picture of its own preloads the artwork,
    exactly as the page itself chooses. Only a plain https address is ever used.
 C. THE FIRST FOUR CARDS LOAD AT ONCE on a collection page and on the Prints list (item 1, the collection page's biggest problem): they are in view straight away, and a lazily loaded picture that is already on screen arrives late
    and is what the test counts as the page's biggest paint. The rest still load lazily.
 D. THE SITE'S HASHED CODE FILES ARE CACHED FOR A YEAR (item 2): /assets/(.*) now has the same immutable header as /fonts. Their file names change whenever their contents do, so this is safe. The pages themselves (index.html, every print and
    collection page, the sitemap) are NOT given a long life: a test proves no header rule reaches them.

WHAT THIS DOES NOT DO, AND WHY (please read)
 * IT DOES NOT RESIZE THE PRINT PHOTOS (the other half of item 1). Every print photo is served straight from Creative Hub at its full size. Vercel's built-in image resizing is not switched on by vercel.json for a site like this one:
   it needs a different deployment mode (the Build Output API), which would mean repackaging all 12 server functions: too risky for a launch. The remaining options, for you to decide after re-measuring:
     1. Make smaller copies of the photos when the site is built (needs an image tool added to the build, and the build downloads about 340 pictures each time: a bigger job, needs a preview of its own).
     2. Use a free third-party image service (NOT recommended: visitors' addresses would go to a company your privacy policy does not name).
     3. Ask Creative Hub whether it offers smaller versions of its pictures at another address (the cheapest answer if it does).
 * IT DOES NOT ADD width AND height TO THE IMAGES. PageSpeed flagged it, but the page's layout shift is already 0, and the true sizes of Creative Hub's pictures are not known when the site is built; guessing them could make the page jump.
 * ITEM 4 (render-blocking requests): FINDINGS ONLY, nothing changed. The page's one style file is 39 KB compressed (245 KB raw, 42 KiB of it unused on a given page) and is the only request that blocks painting. The fonts are already set
   to "swap" (font-display: swap on all 24), so they do not block. BUT the bigger limit on first paint is not the style file: the whole site is one 1,016 KB script (292 KB compressed) and a page shows nothing until it has downloaded and run,
   which is why First Contentful Paint is about 3.5 s on both pages. LCP cannot be faster than that, so reaching 4.0 s on a page whose photo arrives after first paint will be tight. Splitting the script by page (item 5) is the next lever
   if this package is not enough. I would not touch the style file: the saving is small and the risk (unstyled flashes) is not worth it.
